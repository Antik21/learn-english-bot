# AGENTS.md

## Цель проекта

Проект - Telegram-бот для помощи в изучении английского языка.

Бот должен создавать для каждого пользователя персональное учебное пространство, где хранятся:

- интересные пользователю грамматические правила;
- тематические наборы слов;
- слова, которые пользователь сам добавил для изучения;
- будущие результаты квизов, прогресс и предпочтения пользователя.

## Бизнес-логика и фичи

Фичи отсортированы по возрастанию сложности реализации.

| Сложность | Фича | Статус | Описание |
| --- | --- | --- | --- |
| Низкая | Базовый Telegram-бот | Готово | Бот имеет точку входа, запускается через polling и обрабатывает команду `/start`. |
| Низкая | Профиль пользователя | Готово частично | При первом обращении создается пользователь с Telegram ID и языком интерфейса Telegram. Полное пользовательское пространство будет расширяться дальше. |
| Низкая | Выбор тем обучения | Не готово | Пользователь выбирает интересные темы на старте и может менять их позже через меню бота. |
| Низкая | Ручное добавление слов | Не готово | Пользователь может добавить слово или фразу для изучения, указать перевод и при необходимости тему. |
| Средняя | Flow-инфраструктура | Готово частично | Состояние пошаговых процессов хранится в базе. Flow можно начать, продолжить и завершить. Первый flow - onboarding. |
| Средняя | Onboarding пользователя | Готово частично | `/start` запускает или продолжает onboarding. Сейчас есть приветствие, выбор языка страницами по 5 языков и завершение с коротким подтверждением. |
| Средняя | Тематические наборы слов | Не готово | Бот хранит и показывает наборы слов по выбранным темам, связывает их с пользователем и его прогрессом. |
| Средняя | Грамматические правила | Не готово | Бот хранит правила, примеры и объяснения, которые интересны конкретному пользователю. |
| Средняя | Учебный прогресс | Не готово | Бот хранит историю изучения слов, правил, квизов, количество правильных и неправильных ответов. |
| Средняя | Amplitude-аналитика пользовательского поведения | Не готово | Бот будет отправлять продуктовые события в Amplitude, чтобы анализировать путь пользователя, интерес к фичам и проблемные места обучения. |
| Средняя | Квизы с Telegram-кнопками | Не готово | Бот отправляет слово на языке пользователя и варианты перевода в виде inline/reply-кнопок Telegram. |
| Средняя | Повторение сложных слов | Не готово | Слова с ошибками чаще появляются в квизах и повторениях. Конкретный алгоритм нужно согласовать перед реализацией. |
| Высокая | AI-генерация учебных материалов | Не готово | Бот отправляет строгий промпт в AI, получает JSON с правилами, словами, примерами и сохраняет результат в базу данных. |
| Высокая | Генерация стартовых наборов через AI | Не готово | После выбора тем AI генерирует стартовый набор слов, правил и примеров для пользователя. |
| Высокая | Валидация AI JSON | Не готово | Ответ AI должен проверяться схемами перед сохранением, чтобы некорректные данные не попадали в базу. |
| Высокая | Аудио с произношением слов | Не готово | Бот генерирует или получает аудио произношения слов и отправляет его пользователю. |
| Высокая | Персонализация обучения через AI | Не готово | AI помогает подбирать новые слова, правила и предложения на основе интересов, ошибок и прогресса пользователя. |

Если при разработке бизнес-фичи есть несколько возможных вариантов поведения, UX-сценариев, алгоритмов или структуры данных, перед реализацией нужно задать пользователю уточняющий вопрос и не выбирать бизнес-логику молча.

## Работа с базой данных

Доступ к данным должен быть реализован через интерфейсы репозиториев или сервисов, а не через прямые SQL/ORM-вызовы из обработчиков Telegram.

Минимальные требования:

- Telegram-обработчики не должны знать, какая база используется под капотом.
- Для разработки используется SQLite, чтобы проект легко запускался на Windows.
- Для продакшена должна быть предусмотрена замена на PostgreSQL без переписывания бизнес-логики.
- Схема базы должна меняться через миграции Alembic.
- Тесты бизнес-логики должны уметь запускаться на временной SQLite-базе или через in-memory реализации репозиториев.

Пример архитектурного направления:

- `repositories` - интерфейсы и реализации доступа к данным;
- `services` - бизнес-логика обучения, квизов, генерации материалов;
- `bot` - Telegram handlers, routers, keyboards, middleware;
- `messengers` - общий контракт взаимодействия с мессенджерами и адаптеры конкретных клиентов;
- `integrations` - AI, Telegram-specific gateway, будущая аудиогенерация;
- `models` или `db` - SQLAlchemy-модели и миграции;
- `schemas` - Pydantic-схемы входных и выходных данных.

На раннем этапе приложение может создавать SQLite-схему через SQLAlchemy `create_all` при запуске. Перед появлением сложной схемы и продового деплоя нужно перейти на Alembic-миграции.

## Messenger Clients

Основной фокус проекта сейчас - Telegram, но бизнес-логика должна постепенно отделяться от конкретного мессенджера.

Требования:

- Мессенджер должен рассматриваться как клиентский модуль, который запускает бота, принимает события пользователя и отправляет ответы.
- Общая бизнес-логика не должна напрямую зависеть от типов конкретного SDK, например `aiogram.Message` или `aiogram.CallbackQuery`.
- Клиент мессенджера должен преобразовывать входящие события в общий внутренний контекст.
- Бизнес-логика и flow должны возвращать нейтральные действия отправки: текст, кнопки, редактирование сообщения, ответ на callback, будущие аудио/media действия.
- Конкретный адаптер мессенджера должен превращать эти действия в API-вызовы своего SDK.
- Расширять контракт нужно постепенно, от реальных потребностей Telegram-фич, без преждевременного усложнения под будущие платформы.
- Если будущий мессенджер не поддерживает какую-то возможность Telegram, нужно явно описывать fallback-поведение в `AGENTS.md` соответствующего адаптера.

## Flows

`Flow` - это пошаговый пользовательский процесс, в котором бот отправляет запрос, команду или рекомендацию, а пользователь отвечает сообщением или нажатием кнопки.

Требования:

- Flow должен быть гибким и расширяемым.
- Flow должен уметь начинаться, продолжаться с сохраненного шага и завершаться.
- Состояние активного flow хранится в базе данных.
- Telegram handlers не должны содержать всю логику flow; они должны передавать управление flow-сервисам и исполнять возвращенные messenger-действия через адаптер.
- Flow не должен напрямую отправлять сообщения через SDK мессенджера.
- Каждый нетривиальный flow должен жить в отдельной feature-папке и иметь локальный `AGENTS.md`.
- Если пользователь прервал процесс и позже вернулся, бот должен продолжить flow с сохраненного шага, когда это возможно.
- Если при добавлении шага есть несколько вариантов UX или бизнес-логики, нужно сначала уточнить решение у пользователя.

Первый flow проекта - onboarding пользователя.

Текущий onboarding:

- при `/start` бот создает или находит пользователя;
- если onboarding уже завершен, бот отправляет обычный стартовый ответ;
- если onboarding не завершен, бот создает или продолжает onboarding flow;
- шаг `welcome` отправляет приветствие `Привет`;
- шаг `choose_language` предлагает выбрать язык кнопками;
- на странице выбора языка показывается 5 языков и кнопка `Еще`;
- кнопка `Еще` открывает следующую страницу языков;
- после выбора языка бот сохраняет `base_language`, завершает onboarding и отправляет короткое подтверждение.

## Аналитика

В проекте планируется подключение Amplitude для анализа пользовательского поведения.

Требования:

- Аналитика должна быть отделена от бизнес-логики через отдельный сервис или интерфейс клиента аналитики.
- Отправка аналитики не должна ломать пользовательский сценарий, если Amplitude временно недоступна.
- Нельзя отправлять в аналитику секреты, токены, приватные сообщения пользователя и другие чувствительные данные.
- По мере разработки новых фич нужно предлагать варианты добавления аналитических событий.
- Каждое предложение по новому событию должно описывать цель ивента и то, что полезного можно будет анализировать с его помощью.
- Если событие влияет на приватность, состав payload или продуктовую интерпретацию, перед реализацией нужно уточнить решение у пользователя.

## Правила написания кода

- Каждый файл с кодом не должен превышать 400 строк. Если файл растет больше лимита, нужно выделить отдельный модуль, сервис, схему, репозиторий или набор тестов.
- Архитектура должна оставаться расширяемой для новых фичей без чрезмерного усложнения.
- Фичи желательно разбивать по отдельным папкам, чтобы связанная бизнес-логика, Telegram UI, схемы и тесты были сгруппированы рядом.
- В папках крупных или нетривиальных фичей нужно создавать собственный `AGENTS.md` с детальным, но кратким описанием бизнес-правил, технических особенностей, ограничений и статуса фичи.
- Бизнес-логика должна находиться в сервисах, а не в Telegram handlers.
- Telegram handlers должны быть тонкими: разобрать вход, вызвать сервис, вернуть ответ пользователю.
- Основной код должен покрываться тестами.
- Для новых бизнес-фичей нужно добавлять или обновлять тесты.
- AI-ответы нельзя сохранять в базу без валидации схемой.
- Промпты к AI должны быть строгими и версионируемыми в коде.
- Не смешивать инфраструктурный код, бизнес-логику и Telegram UI в одном модуле.
- Конфигурация должна передаваться через настройки и переменные окружения, а не хардкодиться.
- Секреты, токены и ключи API нельзя коммитить в репозиторий.

## Стабильность и сетевые ошибки

Работа бота должна быть стабильной и предсказуемой.

Требования:

- Сетевые ошибки Telegram API, AI API и других зависимых сервисов должны логироваться.
- Повторы запросов допустимы только тогда, когда есть уверенность, что запрос точно не был обработан Telegram-сервером или другим зависимым сервером.
- Для неидемпотентных операций нельзя делать слепой retry, если есть риск повторной отправки сообщения, повторного списания лимитов или повторного сохранения данных.
- Для идемпотентных операций можно использовать retry с ограничением количества попыток и backoff.
- Ошибки внешних сервисов не должны ломать весь процесс обработки обновлений бота.
- Пользователь должен получать понятное сообщение, если операция временно недоступна.
